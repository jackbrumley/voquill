# Release Process

This is the single, ordered procedure for releasing Voquill. Follow it exactly.
Release identity (tag, title, asset names, download links) is consumed by
`install.sh`, `install.ps1` and the in-app updater, so a format mistake is not
cosmetic: it breaks updates and one-line installs for every user.

## Format Rules

Every place the version appears, using `1.7.4` as the example:

| Where | Format | Example |
|---|---|---|
| `package.json`, `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json` | `X.Y.Z` | `1.7.4` |
| Version bump commit message | `chore: bump version to X.Y.Z` | `chore: bump version to 1.7.4` |
| Git tag | `vX.Y.Z` | `v1.7.4` |
| GitHub release title | `vX.Y.Z` (no "Voquill") | `v1.7.4` |
| First line of the release notes | `# Voquill vX.Y.Z` | `# Voquill v1.7.4` |
| Asset file names | `voquill-X.Y.Z-<os>-x64[-setup].<ext>` | `voquill-1.7.4-linux-x64.deb` |
| Download URLs | `.../releases/download/vX.Y.Z/voquill-X.Y.Z-...` | tag keeps the `v`, file name does not |

Rules:
- The version is plain `MAJOR.MINOR.PATCH`. No `-beta.1` or other suffix: the
  extra hyphens collide with the asset name separators. `package-release.mjs`
  enforces this.
- Asset names and download links are generated by scripts from
  `scripts/release-assets.mjs`. Never type or edit them by hand.

## Branches

Development happens on `dev`. A release is tagged on `dev`, then `dev` is merged
into `main`, and `staging` is fast-forwarded to `main`, so all three contain the
tagged commit.

## 1. Bump the Version

Set the same `X.Y.Z` in:
1. `package.json`
2. `src-tauri/Cargo.toml`
3. `src-tauri/tauri.conf.json`

Then refresh the lockfiles so they carry the new version:
```bash
npm install --package-lock-only
cargo update --workspace --manifest-path src-tauri/Cargo.toml
```

Commit exactly these five files (never `git add .`; other work may be in the tree):
```bash
git add package.json package-lock.json src-tauri/Cargo.toml src-tauri/Cargo.lock src-tauri/tauri.conf.json
git commit -m "chore: bump version to X.Y.Z"
```

## 2. Tag and Merge

```bash
git tag vX.Y.Z
git push origin dev vX.Y.Z

git checkout main
git merge dev
git push origin main

git checkout staging
git merge --ff-only main
git push origin staging

git checkout dev
```

## 3. Build and Package Linux

On a Linux machine with `podman`:
```bash
npm run release:linux
node scripts/package-release.mjs
```

`release:linux` builds inside an Ubuntu 22.04 container
(`src-tauri/packaging/linux/Containerfile`). Linux binaries link against the
glibc of the machine that builds them, and the AppImage also bundles that
machine's libraries, so a build on a recent distro (e.g. Fedora 44, glibc 2.43)
will not start on older ones. The container pins the floor at glibc 2.35
(Ubuntu 22.04 / Linux Mint 21 / Debian 12 and newer). Bundles are written to
`src-tauri/target/linux-release/bundle`, the only Linux location
`package-release.mjs` reads from. A host `npm run tauri:build` is for local
testing only and is never packaged for release.

The first run builds the image and compiles from scratch; later runs reuse the
`voquill-linux-release-cache` podman volume (Cargo registry, build target, npm cache).

`package-release.mjs` empties `release-artifacts/` and fills it with the
correctly named files for the current platform only. It skips stale bundles
whose embedded version does not match `tauri.conf.json`. Expected Linux output:
- `voquill-X.Y.Z-linux-x64.AppImage`
- `voquill-X.Y.Z-linux-x64.deb`
- `voquill-X.Y.Z-linux-x64.rpm`

## 4. Write the Release Notes

Generate the skeleton:
```bash
npm run --silent release:notes > release-notes.md
```

stdout is the notes skeleton; the commits since the previous tag are printed to
the terminal (stderr) as source material. Fill in every `TODO` line, keeping
this structure (see v1.7.3 and v1.7.5 for complete examples):

```markdown
# Voquill vX.Y.Z

Voquill vX.Y.Z is a ... release, <one paragraph summarising the headline changes>.

---

## What's New

### Theme Name
- Short Label: One user-facing sentence about the change.

---

### Another Theme
- Short Label: One user-facing sentence about the change.

---

## Downloads

<generated block: all five links, never edited>
```

Content rules:
- Cover everything since the last release that was promoted to latest, not just
  since the previous tag. A pre-release that was never promoted (e.g. v1.7.4)
  was never offered to users, so its changes belong in these notes too: run
  `git log --no-merges --format='- %s' vLAST_LATEST..vX.Y.Z` for the full list.
- Write for users, not developers: describe what changed for them. No commit
  hashes, file paths or internal type names.
- Group changes into themed `###` sections, separated by `---`. Bullets are
  `- Label: sentence` with no bold.
- If users must do anything after updating (re-select a setting, re-grant a
  permission), say so.
- Leave out commits that don't affect users (docs, refactors, CI) unless they
  change something users see.
- The Downloads block always lists all five assets, including the Windows ones
  before they are uploaded. Never remove or reorder links.
- Wrap anything containing angle brackets in backticks (e.g.
  `` `config.json.invalid-<date>` ``); GitHub otherwise hides `<...>` as HTML.
- Before publishing, `grep TODO release-notes.md` must return nothing.

## 5. Create the Pre-Release

Always create the release as a **pre-release**. GitHub's `/releases/latest`
skips pre-releases, so the in-app updater and the install scripts cannot see it
until it is promoted in step 8.

```bash
gh release create vX.Y.Z --verify-tag --prerelease --title vX.Y.Z --notes-file release-notes.md
```

## 6. Upload the Linux Assets

```bash
gh release upload vX.Y.Z release-artifacts/*
```

Confirm each digest GitHub computed matches the local file (the installers
verify downloads against these digests; no `.sha256` files are uploaded):
```bash
gh release view vX.Y.Z --json assets --jq '.assets[] | "\(.digest)  \(.name)"'
sha256sum release-artifacts/*
```

## 7. Build, Package and Upload Windows

On a Windows machine, check out the `vX.Y.Z` tag, then:
```bash
npm run tauri:build
node scripts/package-release.mjs
gh release upload vX.Y.Z release-artifacts/voquill-X.Y.Z-windows-x64-setup.exe release-artifacts/voquill-X.Y.Z-windows-x64.msi
```

Expected Windows output:
- `voquill-X.Y.Z-windows-x64-setup.exe`
- `voquill-X.Y.Z-windows-x64.msi`

Check the digests as in step 6 (`Get-FileHash` in PowerShell).

## 8. Promote to Latest

Only once all five assets are uploaded. Promoting earlier makes `install.ps1`
and the Windows updater fetch an installer that does not exist (404).

```bash
gh release view vX.Y.Z --json assets --jq '.assets | length'   # must print 5
gh release edit vX.Y.Z --prerelease=false --latest
```

Agents: never promote a release unless the maintainer explicitly asks.

## 9. Verify

- An installed older version offers the update (Settings → General → Check for Updates),
  and the update installs and relaunches.
- The one-line installers from the README install the new version on a clean
  machine.

## Agent Checklist

- [ ] Tag is `vX.Y.Z`; release title is `vX.Y.Z`; notes start with `# Voquill vX.Y.Z`.
- [ ] Notes come from `npm run release:notes`; no `TODO` remains; Downloads block untouched.
- [ ] Created with `--prerelease`.
- [ ] Assets uploaded only from `release-artifacts/`, never renamed by hand.
- [ ] Release not promoted to latest without the maintainer's explicit instruction.
